# 規則建議研究報告：900 組「同一 KR 不同譯法」

2026-11-12。對象是審核頁「規則建議」列出的全部 `inconsistent` 項目：同一族群、同一欄位、KR 相同，譯法卻不只一種的組。這份報告逐組判斷原因、依內容分類，並給每一類與每一組調整建議。**這份報告不改任何檔案**；每一組的確切改動（改前、改後、單位數、檔案）都列在 `items/` 裡，你逐項或整段同意之後才會寫入。

## 摘要

- 900 組，共 3,370 個單位。建議**保留** 388 組（不改譯文）、**改譯文** 486 組（統一 432、只修錯的 51、加詞條並統一 3，共改 694 個單位）、**交給你決定** 26 組。
- 所有改動都是逐字替換成報告裡寫好的譯文，**沒有任何一組需要重翻**：你同意的文字就是最後的譯文。
- 要改的 694 個單位中，647 個是社群舊譯（Paratranz）、47 個是本專案新譯；沒有人工調整的單位。
- 建議你先決定下面「[需要你先決定的事](#需要你先決定的事)」的六件事，再逐類同意；尤其是 158 組低信心的判讀，不建議整批同意。

## 資料與方法

| 項目 | 版本 |
|---|---|
| 程式與規則 | `main` 9a8e380 |
| 譯文 | `tw` 5f25d25（tw-latest） |
| 原文 | `raw-20261112`（f337c5d） |
| 審核資料 | 以上三者跑 `lct site` 產生的 `data/review/suggestions.json` |

1. **整理資料**：每組的每種譯法加上單位來源（`paratranz`、`claude`、`human`）、說話者（劇情類取 KR 的 `model`／`speaker`）、對應的官方 JP／EN；另標出「只差格式」的組（去掉標籤、統一標點與空白後各譯法相同，101 組）。
2. **逐組判讀**：分成 9 份，由子代理依 [判讀說明](method/GROUPS.md) 逐組判斷。判讀時只能讀，可以用 `lct search` 看單位前後文、查 `guides/` 與 `glossary/`。
3. **驗證**：每組都有判讀、`changes` 的改前文字都逐字等於該組某種譯法、「統一」的每個非目標譯法都有改動。有 2 組漏列了一種譯法的改動，整理時補上（見[整理時的更正](#整理時的更正)）。
4. **組裝**：[`method/assemble.py`](method/assemble.py) 產生 `items/` 與 `data/judgements.json`；每個改動的受影響單位取自審核資料的完整 key 清單。

限制：

- 判讀是模型做的，「信心」是判讀者自評。9 份由不同子代理判讀，同類情況的處理不完全一致（見 [I4](#i4)）。
- 單位清單與改前文字是 tw 5f25d25 的現況。套用時逐字比對整句，現況已經不同的單位不會被改，套用前我會先列出這種單位給你看。
- 關鍵字名稱以外，沒有檢查別的檔案是否也寫了同樣的名稱或句子（見[改關鍵字名稱](#改關鍵字名稱)）。

## 怎麼讀

每組在 `items/<類別>.md` 有一段，標題是：

> `G123　統一｜I4 同義措辭不同｜信心中　⚠ …`

- **G123**：這份報告的編號，同意時用它指稱
- **統一／只修錯的譯法／加詞條並統一／交給你決定／保留**：建議的處理
- **I4**：類別（見[各類別與調整建議](#各類別與調整建議)）
- **信心**：高、中、低
- **⚠ 低信心**、**⚠ 統一後是新寫法**、**⚠ 改關鍵字名稱，別處有引用**、**⚠ 整理時補上一項變更**：需要特別看的組

內容依序是：審核頁上的 id、族群／欄位、單位數、JP/EN 對應情形；KR；現有的每種譯法（單位數、來源、說話者、各自的 JP/EN）；判讀；建議；**會改**（每一項改前 → 改後、單位數、檔案）與**差異**（只標出改動的地方，`〔舊→新〕`，`∅` 表示沒有，`␣` 是半形空格，`⏎` 是換行）；**不改**的譯法；同意後寫入什麼。

`data/judgements.json` 是同樣的內容加上每個改動的完整單位 key 清單，套用時以它為準。

## 怎麼同意

用編號或類別告訴我，例如：

- 「同意 G001–G105」「I1 全部照建議」「I3 全部保留」
- 「G116 選 2」「G789 選 1」
- 「不同意 G045，其他照建議」「G573–G704 改成交給我決定」

同意後寫入的東西：

| 建議 | 寫入 | 譯文 |
|---|---|---|
| 保留 | `rules/declined.yaml` 一筆：`id`、`reason`（判讀的理由）、`date`，經由 `bin/lct accept --reason` 寫入 | 不改 |
| 統一、只修錯的譯法 | 每個「會改」寫一個 `rules/rewrite/<日期>-<主題>.yaml`：`files` 為該項列出的檔案，`origins` 為那些單位的來源，`pattern` 是改前整句（逐字、前後錨定），`kr_pattern` 是 KR 整句，`replace` 是改後整句。套用後這組只剩一種譯法，審核頁自然不再列出（只修錯的譯法若仍留下兩種以上，另把 id 記進 `rules/declined.yaml`） | 下一次 CI 重建時改成報告裡的改後文字 |
| 加詞條並統一 | 上一列的改寫檔，加上 `glossary/terms.yaml` 一個條目（照現有格式：`kr`、`jp`、`en`、`zh`、`status: approved` 等，jp／en 取官方譯名） | 同上；之後的新譯會帶這個詞條 |
| 交給你決定 | 依你選的選項；選「保留」寫 `rules/declined.yaml`，選改寫則同上 | 依選項 |

套用時我會先在本機用最新的 `tw` 試套，確認改到的單位正好是報告列出的那些（數量與 key 都相同），不同就停下來回報；然後經由 `main` 提交，`tw` 只由 CI 寫入。

改寫檔只套用一次：之後新翻的句子不受影響。若希望之後也一致，要靠指引或詞彙表；各類別的建議裡有寫哪些需要。
