# 方法：怎麼從遊戲程式讀出這些規則

這份報告的結論都來自 2026-11-12 版的 `GameAssembly.dll`（Windows x64，165,384,192 bytes）與 `global-metadata.dat`（50,227,844 bytes）。遊戲更新後，位址、enum 成員、甚至規則本身都可能改變，重做時照下面的步驟。

## 1. 還原 metadata

遊戲用 Unity 6000.3.12f1 的 IL2CPP（metadata v39）。`global-metadata.dat` 經過改造，一般的 IL2CPP 工具讀不了：

- 檔頭不是標準的 `0xFAB11BAF` 與版本號，而是 0x324 bytes 的自訂表：67 組 `(大小, 筆數, 位移)`，其中 31 組是真的資料表，其餘是混淆用的假資料；順序被打亂，每張表的實際位移還要再加上一個寫死在程式裡的常數。
- 檔頭與 7 張表（字串常值索引、字串常值、識別字、屬性、方法、欄位、組件）各用一組種子加密：xorshift64（位移 13、7、17）產生狀態，取狀態低 4 個 byte 互相 XOR 後查一張 256 bytes 的替換表，得到的 byte 與資料 XOR。
- 解密程式在 `GameAssembly.dll` 裡，緊接在「開啟 `Metadata\global-metadata.dat`」之後（檔名在堆疊上逐字組出來，所以搜不到字串；從錯誤訊息 `ERROR: Could not open %s` 的引用可以找到載入函式，再找它唯一的呼叫者）。種子、替換表位址、各表的位移常數都從這個函式讀出來。
- 沒有加密的表，位移常數散在各個讀取函式裡，不必逐一找：各表在檔案裡仍照標準順序緊接排列（4 bytes 對齊），用已知的 7 張加密表當定位點，其餘依大小推算，再用內容檢查（名稱索引是否落在字串開頭、遞增欄位是否遞增）確認。這一版只有「欄位封送大小」那張表前面多 4 bytes。
- 解密後依標準 v39 的順序重寫檔頭，就得到一般工具能讀的 metadata：51,653 個型別、322,172 個方法、32,350 個字串常值。

## 2. 反編譯

用 [HZBHZB1234/il2csharp](https://github.com/HZBHZB1234/il2csharp)（r11）：

- `--decls-only` 先輸出 `Assembly-CSharp` 全部型別的宣告（25,318 個檔，約 1.5 分鐘），用來找型別、欄位、方法與位址。
- 需要讀方法內容的型別，用 `--types <名稱>` 個別反編譯（每次約 1 分鐘）。整個 `Assembly-CSharp` 一次反編譯會用光 16 GB 記憶體。
- 這個反編譯器的輸出**不能直接相信**：條件有時相反、`const` 字串是錯的、泛型方法沒有內容。報告裡每一條會影響結論的判斷（例如「名稱後面接什麼字元才連結」），都另外對照反組譯確認過；只看反編譯結果、沒有對照的地方會標「推定」。
- 另外自己做了兩個小工具：從 `call`／`jmp` 指令建立「誰呼叫誰」的索引（找某個函式的所有呼叫者），以及帶方法名稱的反組譯輸出。

## 3. 用官方資料驗證

讀出規則後，寫成 [`kwsim.py`](kwsim.py)，拿 `raw` 分支的 KR／EN／JP 官方文字與 `tw` 分支的譯文檢查：

- 專案裡兩個「已在遊戲中確認」的案例（`rules/adjustments/2026-11-04-noparse.yaml`）都重現：「攻擊等級+1」被讀成 `AttackLevelAdder`、「加斥我援」的「援」被讀成 `CheerUpXichun`。
- KR 官方文字裡被 `<noparse>` 包住或後面接 `[TabExplain]` 的名稱，後一個字元是空格的 206 處、文字結尾 35 處、`,` 28 處、換行 6 處，都符合規則；有 9 處是 `)`，照規則不會連結（官方多包了）。
- JP 官方把「～」「始」「種」三個名稱標成 `excludeAutoLink`，KR／EN 沒有；可見這個欄位是各語言自己決定的。

## 沒有放進版控的東西

解密與分析用的腳本（含這一版的種子）、解密後的 metadata、反編譯輸出都只在工作目錄，沒有放進版控。
