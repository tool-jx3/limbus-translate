# `{0}` 代入的是什麼

2026-11-18。官方 KR 有 2,139 個字串帶佔位符（`{0}`、`{1}`……或 `{reward}` 這類具名記號）。這一章整理每一類代入的是數字、名稱還是另一段文字，以及程式會不會先加好正負號、顏色或單位。程式把幾段文字固定順序接起來的地方見 [09-assembled-text.md](09-assembled-text.md)；格式化出錯時的行為見 [04-other.md](04-other.md) 第 2 節。

依據：讀取各字串並做格式化的函式與它傳入的參數（2026-11-12 版）。標記：

- **確認**：在反編譯或反組譯裡讀到傳入的參數。
- **函式確認**：找到了做格式化的函式與參數的種類，但「第幾個參數對第幾個索引」是照範本推的。
- **從句子推定**：只能從韓文句子判斷。
- **不明**：程式裡找不到引用這個 id 的地方。

涵蓋：

| 範圍 | 字串數 | 確認 | 函式確認／機制已知 | 推定 | 不明 |
|---|---|---|---|---|---|
| 介面文字以外的表 | 1,120 | 964 | 50 | 103 | 3 |
| 介面文字表 | 1,019 | 674（含函式確認） | — | 254 | 91 |

## 先講結論

- **絕大多數是 `string.Format`**：索引可以調換順序、重複使用；索引超出參數個數，或多寫一個 `{`、`}`，會丟出例外，而且多數地方沒有保護。**索引的集合照 KR，不要增減。**
- **數字幾乎都是光溜溜的整數**：沒有正負號、沒有千分位、沒有單位。`%`、`+`、量詞都要寫在範本裡。
- **例外要記住的三類**：
  - 程式**先加好正負號**的數值（狀態能力約 43 個範本、修正值、Project GS 的成長文字）。
  - 程式**先包好顏色標籤**的名稱或數值（十來個介面字串、選擇事件的 `{reward}`）。
  - 程式**先組好的整段文字**（日期時間、「道具名 數量」、另一句介面文字）。
- **代入名稱時是已經翻好的譯名**，而且不含括號與顏色：周圍的字要對任何名稱都通順。
- **同一個索引不一定是同一種東西**：鏡牢起始增益的 `{1}` 可能是狀態名稱，也可能是數字。
- **兩種不是 `string.Format` 的**：選擇事件結果的具名記號、技能標籤的 `{n}`。拼錯的記號會整個消失，不會報錯。

## 1. 共通的積木

| 名稱 | 玩家看到的 |
|---|---|
| 整數 | 半形數字；負數有 `-`；正數沒有 `+`；沒有千分位 |
| 帶號整數 | `+3`、`+0`、`-3`，**正負號是程式寫的** |
| 百分比數值 | `25`、`12.5`，**沒有 `%`**；小數點跟著作業系統的地區設定 |
| 狀態名稱 | `Bufs*` 的 `name`，沒有顏色、沒有連結、沒有括號 |
| 屬性名稱 | `AttributeText` 的 `name` |
| 攻擊類型 | 介面文字的斬擊、突刺、打擊 |
| 罪人名字 | `Characters` 的 `name`，**不含人格稱號** |
| 人格全名 | 稱號＋空格＋名字（稱號裡的 `\n` 還在） |

## 2. 判定事件的結果（`AbEvents*` 的 `successDesc`、`failureDesc`，418 個）

- `{0}` 是**做判定的那位罪人的名字**，只有一個，不含人格稱號（確認）。
- KR 自己在後面接「수감자」，也常寫成 `[{0}]`；同一句裡 `{0}` 最多出現 5 次，都是同一個名字。
- 格式化有保護：出錯時改顯示原始文字。
- 地牢事件另有一條目前不顯示的路徑，傳的是人格全名。句子最好對長名字也通順。

## 3. 狀態（`Bufs*` 的 `desc` 208 個、`summary` 115 個）

| 狀態的種類 | `{0}` | `{1}` | `{2}` |
|---|---|---|---|
| 一般狀態 | 層數 | —（寫了會出錯） | — |
| 有強度與回數的狀態（燒傷、流血、震顫、破裂、沉淪、呼吸等） | 強度 | 回數 | — |
| 充能類 | 強度 | 回數 | 累計消耗的回數 |

- **只有 `{2}` 的 8 個字串**就是充能類：`{0}`、`{1}` 可以用，只是原文沒用。
- 少數狀態有自己的參數（確認），例如：
  - `TimeRentalTwo`：`{0}`＝層數×2−2，`{1}`＝回數−1，可能是 0。
  - `TimeSuspend`：用 `{0}`、`{2}`、`{3}`（層數、累積傷害、換算後的數值）。
  - `SinkingWhite`：`{2}`、`{3}` 是能力裡設定的數值。
  - `BloomingRose`、`EatingSin`：`{1}`、`{2}` 是兩個名稱（屬性與人格，來源表沒有追到）。
  - `TakePicture`：`{0}` 是上一回合最後用的技能名稱。
- **沒有任何保護**：索引超出範圍，提示框整個壞掉。
- **`summary` 會決定 `desc` 拿到幾個參數**：有回數的狀態走一條分支時，程式數 `summary` 裡有幾個不同的索引，超過一個就傳「層數、回數」，否則只傳「層數」。所以 `desc` 與 `summary` 的索引集合都要與 KR 相同。
- **會原樣顯示的情況**：文字裡沒有 `{0}` 時，有兩條路徑不做格式化。只寫 `{1}` 而沒有 `{0}` 的文字，可能把 `{1}` 直接顯示出來。
- `{0:F1}`（13 個抗性字串）的格式會被照做；傳進來的是哪個數值取決於遊戲的靜態資料，沒有確認。
- 這條路徑沒有程式加的 `%`、正負號或單位，`{0}x5%` 這種寫法裡的符號都是範本的。
- 41 個字串的歸屬是用「id 就是類別名稱」推的。

## 4. 狀態能力的範本（`BuffAbilities` 的 `desc` 88 個、`variation`、`variation2`）

範本的 id 就是能力類別的名稱，88 個類別各自決定參數（79 個確認）。

**數值已經帶正負號的**（約 43 個範本）：`AtkAdder`、`SkillPowerAdder`、`PlusCoinScaleAdder`、`MaxSpeedAdder`、`DefAdder`、`AtkDamageMultiplier`、`MaxHpMultiplier` 等。

- 代入的是 `+3`、`+0`、`-3`。**譯文不要再寫 `+`。**
- 百分比類代入的數值沒有 `%`，`%` 要留在範本裡。
- 官方 KR 有兩個範本自己多寫了正負號：`MRR541`（`+{0}`）與 `CoinScaleAdderByAtkType`（`+{1}`／`-{1}`），遊戲裡會顯示成兩個正負號。現行譯文照 KR 也有。

**代入狀態名稱的**（26 個範本）：

| 範本 | 名稱在哪個索引 | 其他索引 |
|---|---|---|
| `TakeBuffTurnAdder` | `{0}` | `{1}`＝帶號的回數 |
| `GiveBuffOnReleaseStandBy`、`MRR552` | `{0}` | `{1}`＝層數 |
| `GiveBuffOnFirstRoundStartPerWave`、`MRR551` | `{0}` | `{1}`＝層數，`{2}`＝回數 |
| `GiveBuffOnRoundStartToAllAlly` 系列 | `{0}`（最多用 4 次） | `{1}`、`{2}`＝層數與回數的量 |
| `MD7LimitGiveBuffAllyDie` 系列 | `{0}` | 層數、回數、上限 |
| `CriticalDamageBoostWithBuffUse` | `{0}` | `{1}`＝層數，`{2}`、`{3}`＝百分比數值 |
| `LacerationStackAndTurnAdder`、`MRR541` | **`{1}`** | `{0}`＝帶號整數 |
| `GiveBuffOnBattleStartAR` | **`{1}`** | `{0}`＝屬性名稱，`{2}`＝層數，`{3}`＝回數 |
| `MRR512` | **`{1}`** | `{0}`、`{3}`＝數值，`{2}`＝層數 |
| `MRR506` | `{0}`、`{2}`、`{3}`（三個不同的狀態） | `{1}`＝屬性名稱 |
| `MRR536` | `{0}`、`{1}`（兩個狀態） | |
| `MRR524P`、`MRR540`、`MRR5052`、`MRR507`、`MRR508`、`MRR557` | `{0}` | |

- `variation`、`variation2` 是條件不同時改用的範本（例如回數是 0 時改用不提回數的那一句），索引的意思跟著變。
- **產生出來的句子會再被格式化一次**：程式把各條能力接成「`* `＋句子＋換行」，再交給狀態的提示框格式化。所以這些範本裡不能有任何多餘的大括號。
- 有 8 個範本（震顫系列等）自己不格式化，由所屬的狀態用「層數、回數」處理。
- `GiveBuffOnSucceedAttack` 在程式裡找不到對應的類別（不明）。

## 5. 鏡牢起始增益（`DungeonStartBuffs*` 的 `description`，97 個，確認）

| 情況 | `{0}` | `{1}` | `{2}` | `{3}` | `{4}` |
|---|---|---|---|---|---|
| 效果會給一個狀態 | 效果的數值 | **狀態名稱** | 層數 | 回數 | 上限（樓層或解鎖數的門檻） |
| 其他 | 效果的數值 | **第二個數值**（例如上限） | — | — | — |

- 所以 `{1}` 是名稱還是數字，依 id 而定。只用 `{1}`、`{2}`、`{4}` 的字串沒有 `{0}`、`{3}`，是因為用不到。
- 都是整數，沒有正負號。`%`、`+`、「(最大 9)」都是範本的字。
- 各條效果由程式用換行接起來；另一種顯示方式每條前面加「• 」。
- 找不到狀態名稱時代入一句寫死的韓文。

## 6. 精神狀態（`MentalCondition*` 的 `add`、`min`）

- `{i}` 是條件 id 裡**第 i+1 個數字**（確認）；數字沒有正負號，所以「增加」「減少」要由句子表達。
- 規則：文字裡**不同索引的個數**必須等於 id 裡數字的個數，否則這一行不顯示。`{0}` 重複出現只算一次。
- 個數對了但索引寫錯（兩個數字卻寫 `{0}`、`{2}`）會通過檢查，然後出錯。
- 每個數字代表什麼（基本值、每次拼點增加的百分比、上限、門檻）要看條件 id，而條件 id 不在語言包裡，只能從句子推定。

**Project GS 的成長結果（`reward-popup-text-ProjectGS`）**：

- 只讀 `add`；**`min` 的 19 個字串沒有人讀**。
- `{0}` 是罪人名字（不含稱號）。
- `{1}` 依類別：整數；可能是負數的兩位小數（抗性）；**技能名稱或被動名稱**。升級技能時還有 `{2}`。

## 7. 選擇事件結果的具名記號（`ChoiceEventEffect*`，28 個，確認）

不是 `string.Format`：程式用 `{`、`}` 把範本切開，逐段去問「這是不是記號」。

| 記號 | 換成什麼 |
|---|---|
| `{conditions}` | `ChoiceEventKeyword` 的片段；判定成功／失敗的條件後面程式會加一個半形空格；屬性條件裡的屬性名稱各自有顏色，用 `", "` 接 |
| `{targets}` | `ChoiceEventTarget` 的片段；指定角色時是罪人名字，多位用 `", "` 接 |
| `{amount}` | 整數，沒有正負號；`%`、單位是範本的字 |
| `{hpAmount}`、`{mpAmount}` | 兩個整數 |
| `{reward}` | 飾品名稱，**程式已經包好顏色標籤**；飾品沒有顏色資料時是空的，記號就消失 |
| `{stack}` | 數量 |
| `{waveNum}` | 數字 |

- **只認這 8 個名稱**。其他的（拼錯的、翻譯過的）會整個消失，不報錯。官方 `GetBuff_OnStageStart` 那一句用的四個記號都不在名單裡，連官方自己都不顯示。
- 可以調換順序、重複、省略。唯一的限制：第 n 個 `{conditions}` 對第 n 個條件。
- `{conditions}` 與 `{targets}` 之間的空格、多個名稱之間的 `", "` 是程式寫的半形字元。
- `{reward}` 自帶顏色，放在範本的顏色標籤裡時要維持巢狀。
- 每一段普通文字都會被當正規表示式編譯（[04-other.md](04-other.md)）。

**`{affectedTarget}`**（`ActionEvents*` 的結果）：全隊都受影響時換成介面文字的「全部」，否則是受影響角色的名字用 `", "` 接。句子要兩種都通順。

**技能標籤的 `{n}`**（`SkillTag` 的 `name`）：單純的字串取代，換成技能文字裡那個標籤寫的數字。可以移動、重複；拿掉的話數字就不顯示。

## 8. 介面文字表

### 個人檔案的問候語（`introduce_sentence_*`，273 個，確認）

- `{0}` 是玩家另外選的一個詞（`introduce_word_*` 的整段文字，共 274 個），原樣插入，沒有引號、顏色或分隔。
- **句子與詞是各自獨立挑的，沒有類別對應**：任何詞都可能進任何句子。所以 `{0}` 周圍的字要對擬聲詞、暱稱、名詞都通順。
- 只有一個參數；`{0}` 可以重複（官方有一句用了 9 次）。
- 選擇畫面上，詞的位置顯示 `■■■■■`。
- KR 句子裡的 `(은/는)` 這類記號只在遊戲內選 KR 時處理；中文不要照抄。

### 選擇事件的結果紀錄（`AbEventsResultLog*`，260 個）

- 參數是每個事件的程式寫死的（62 個事件類別），不是資料。
- 參數的種類（函式確認）：

| 種類 | 看到的 | 次數 |
|---|---|---|
| 數字 | 整數，沒有正負號、`%` | 248 |
| 狀態名稱 | `Bufs*` 的 `name`，沒有括號與顏色；會讓一組 `%…/%` 上色 | 162 |
| 敵人或異想體的名稱 | 敵人名稱表的 `name` | 72 |
| 罪人名字 | 不含人格稱號 | 52 |
| 技能、被動、屬性、攻擊類型的名稱 | | 13 |
| 寫死的字串 | 只有一個事件：`+10`／`-10`（帶正負號），以及包好顏色的屬性名稱 | 6 |

- 常見的句型：`[{0}] %[{1}] {2}/%`＝單位名稱、狀態名稱、層數；`[{0}] … {1} …`＝單位名稱、數字。括號是範本的字。
- 「第幾個索引是什麼」在 3 個事件類別確認過；其餘 59 個是照句型推的。
- **規則**：
  - 不同索引的個數要與 KR 相同，否則**完全不代入**（不會出錯，直接顯示 `{0}`）。
  - 每一組 `%…/%` 都要留著，彼此的先後順序不變；狀態名稱的索引留在它自己那一組裡，因為顏色跟著那一組。
  - `/%` 後面緊接的半形 `,`、`.` 會被移到顏色標籤外面；全形標點不受影響。
- 37 個 id 在程式裡找不到引用（包含 `chracter_hp_increase` 這類通用的），可能已經不用。

### 任務標題（`mission_ui_condition_tags_*`，118 個）

- 參數來自任務條件的靜態資料裡的一串標籤（機制確認）：目標數值、各條件的最小／最大值是整數；角色、關鍵字、飾品分類是名稱，多個用 `", "` 接。
- 每個 id 用了哪些標籤不在語言包裡。官方 118 句讀起來每個索引都是數字（從句子推定）。
- 參數個數由資料決定：不要增加 KR 沒有的索引。

**已經組好的整段文字**：

| id | 內容 |
|---|---|

| `dungeon_battle_reward_case_format_*` 的 `{0}` | 數字，或「最小~最大」 |

| 四個飾品的 `desc` | `{0}` 是一整句介面文字，自成一行 |
| `walpu_battle_result_win/lose_*` | `{0}` 是另一個介面字串（戰鬥的名稱） |

**特殊語法**：`correction_based_on_association`、`correction_based_on_unit_keyword`

- 程式在**第一個半形 `(`** 把字串切開：前面是範本，結尾括號裡的字是清單的分隔。
- 所以範本裡不能有其他半形 `(`；結尾的 `( … )` 要留著。想換分隔就改括號裡的字。全形括號不受影響。
- 現行譯文（`{0} 所屬變動值 {1}(, )`）符合。

**不做格式化的**：`coupon_use_failed_2`～`6` 等直接顯示，寫了 `{0}` 會原樣出現。

**年月日是分開的整數**（`open_scheduled_date_month_day`、`event_for_new_user_from_date` 等），中文可以自由排順序。

**參數比用到的多是正常的**：例如 `project_gs_growth_desc` 傳 8 個只用 6 個。

## 9. 對譯文的規則整理

1. 索引的集合與 KR 相同；`Bufs*` 的 `desc` 與 `summary` 兩邊都要。不要用 `{{`、`}}`。
2. 狀態能力的範本：KR 沒有寫 `+` 的地方不要加；`%` 留在範本裡。
3. 代入名稱的位置，周圍的字要對任何名稱都通順；不要假設名稱帶稱號。
4. 包好顏色的值不要再包顏色；`{reward}` 放在顏色標籤裡時維持巢狀。
5. 具名記號照抄，不翻譯、不改拼法。
6. `AbEventsResultLog*`：`%…/%` 的組數與先後順序照 KR，狀態名稱的索引留在自己的那一組裡。
7. 問候語的 `{0}` 可以是任何詞：句子不要依賴詞性。
8. 不要照抄 KR 的助詞記號（`을(를)`、`(은/는)`）。
