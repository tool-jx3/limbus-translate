# 翻譯品質：指引分檔、詞彙詞義、應用率回顧、舊譯複查與基準

日期：2026-11-06。狀態：使用者已核可（2026-11-07；基準樣本每族群 20 個）。

## 背景與目的

真實資料（raw-20261105，2,422 檔、272,875 單位）：

- **來源比例**：不含 copy 的 181,914 單位中，163,812（90%）是 Paratranz 舊譯，Claude 18,077，人工 25。現行規則只作用在新送翻的單位；舊譯除非 KR 改版或有人 requeue，不會被重看。
- **審核訊號**：
  - 500 組不一致譯法；
  - 192 個詞條、2,335 單位沒用譯名，其中只有 7 個有 note 說明；
  - 231 個格式警告。
- **指引**：16 個族群的 `guide:` 都指向 `guides/families.md`。那份檔案寫的是檔名規則與翻譯優先序，不是翻譯規則。各文本類型都沒有專屬規則，全部擠在 `base.md`（178 行，通用規則）。
- **詞彙表**：595 條，JP 只填 13 條、EN 26 條，`notes` 多為來源說明。一詞多義的詞（대상、관리자、날개…）全靠譯者猜。
- **應用率**：
  - 有命中的 592 條中，400 條 100%，192 條未滿：114 條 ≥95%、69 條 80–95%、9 條 50–80%。
  - 前 20 條就占了缺漏單位的 71%。
- **品質量測**：沒有基準，無法知道改規則是否讓譯文變好。

使用者要做的四件事（建議清單第 2–5 項），全部完成後才合併：

- A 指引依分群分檔並組合；
- B 詞彙補 JP、EN、詞義，不得編造；
- C 依分群回顧應用率未滿 100% 的詞條；
- D 舊譯分批複查的工具與基準樣本。

## 共同原則

- **規則只寫在 `guides/`、`glossary/`、`rules/`**，程式只負責組合與檢查（CLAUDE.md）。
- **不編造**：
  - 每條新寫的規則、詞義、JP/EN 都要有出處：遊戲檔案的 key、wiki.gg 網址，或現有譯文的統計（附單位數）。
  - 找不到出處就留空。
  - 新增的規則與詞彙內容由使用者在合併前審閱。
- **不在這次工作花翻譯費用**：
  - 合併到 `main` 時若 `rules/` 有變更，會觸發 rebuild；rebuild 會翻待譯清單（預設上限 30 美元）。
  - 這次只交付工具與第一波的候選清單，不提交 `rules/requeue/` 的重翻申請；何時重翻由使用者決定。
  - A、B、C 會改 `guides/`、`glossary/`，合併時會觸發 rebuild，但不會產生新的待譯單位（詞彙與指引不使舊譯重翻），所以 rebuild 只會重建語言包。

## A. 指引分檔與組合

**現況問題**：每批都送 `families.md`（約 10 KB 的檔名規則），浪費篇幅也沒幫助；各文本類型的慣例散落或不存在。

**做法**：

1. `guides/families.md` 改為給人看的參考文件，不再列在任何族群的 `guide:`。
2. 每個族群一份短指引 `guides/families/<id>.md`，共 16 份，內容固定四節：
   - 文本類型；
   - 語氣與人稱；
   - 格式慣例（標籤、`[ID]`、數字、標點、換行）；
   - 常見錯誤。

   內容來源有兩種，每條都要附出處：
   - **現有規則**：`base.md`、詞彙 notes、`rules/adjustments` 中只適用於該族群的部分（搬移，不重複）；
   - **現有譯文的統計**：從該族群已核可的譯文歸納慣例，例如技能說明的觸發條件寫法、UI 按鈕用語。只寫出現率夠高的慣例（≥80% 且 ≥30 單位），並附例子與數字。

   每份上限 4 KB。
3. **更細的層**：`routing.yaml` 新增 `guides:` 清單，每項 `{when: <條件>, guide: <檔>}`。條件可寫：
   - 節點樣式（同 `nodes`）；
   - 標記 `chapter:<n>`、`character:<id>`、`event:<id>`（同詞彙範圍的寫法）。

   `GuidesFor` 的組合順序是：base → 族群 → 符合的節點 → 符合的標記 → 說話者角色指引。這次只建機制，再依證據加少數幾份；沒有證據就不寫。
4. **檢查**：
   - `lct rules lint` 檢查指引檔存在、每份 ≤4 KB、每批組合後總量 ≤ 現在的 34 KB；
   - 預覽頁可直接看組合結果；
   - `prompts/translate.md` 說明疊加順序。

### A 的追加決定（2026-11-07，使用者審閱後）

- **括號**：base.md 第 7 條改為括號用全形「（）」。戰鬥說明類族群（ally、enemy、keywords、mirror）維持半形，因為既有譯文約 95% 是半形。
  - 這兩條各自以改寫檔（`rules/rewrite/`）把少數不符的舊譯機械式統一，不送翻譯。
  - 既有例外照舊：非劇情檔的 ruby「Y(X)」、亂碼符號。
- **共用指引**：跨族群、但不是所有族群都用的規則，寫成共用檔 `guides/shared/<主題>.md`。用到的族群在 `routing.yaml` 以 `include:` 引入。
  - 組合順序：base → 族群 → 該族群的 include（依序）→ 節點層 → 標記層 → 角色。
  - 共用檔同樣每份上限 4 KB，同樣附出處；統計以引入它的族群合計。

## B. 詞彙補 JP、EN、詞義

**新欄位**：

- `meaning`：zh-TW 一兩句詞義，說明這個詞在遊戲中指什麼、何時不適用；
- `sources`：出處清單，每項是 `game:<檔名>#<pointer>` 或 `https://limbuscompany.wiki.gg/...` 的網址。

`jp`、`en` 已存在。

- **lint 規則**：有 `meaning` 就必須有 `sources`；網址只允許 wiki.gg。
- **批次**：本來就帶 jp、en，改為一併帶 `meaning`。`prompts/translate.md` 說明如何用它們判斷是否同義。

**資料來源**，依可靠度：

1. **遊戲名稱表**：KR 等於整個單位文字的名稱欄位，例如 keyword 的 `name`、E.G.O 飾品名、人格名。同一單位對齊的 JP/EN 就是官方名稱，完全精確。keyword 的 `desc` 是官方說明，可作為詞義出處。
2. **對齊驗證**：對非名稱的一般詞，先產生 JP/EN 候選（來自名稱表、wiki 標題，或由代理人從單位三語對照提出），再驗證後才採用：
   - 候選必須出現在 ≥60% 含此詞且有對齊的單位中；
   - 至少 10 個單位；
   - 同時記下命中比例。
3. **wiki.gg（英文）**：
   - 這個環境可用 MediaWiki API 讀取，namu.wiki 與 wikiwiki.jp 會被網站擋，不使用；
   - 只用於詞義；
   - 摘要成 zh-TW 時保留原意，`sources` 記網址。

**工具**：`lct glossary evidence` 為每個條目輸出候選與證據（JSON 與報告），用來填 jp/en/meaning/sources；不會自動改 `terms.yaml`，由人或代理人依報告寫入。

**範圍**：
- 先補應用率未滿 100% 的 192 條與一詞多義的條目；
- 其餘條目有精確名稱表來源的才補。

## C. 應用率回顧

1. `lct glossary scope` 為每個未滿 100% 的條目，依族群與 top 節點分組。條目有 jp/en 時，再把缺漏的單位分成兩類：
   - **同義**：對齊的 EN/JP 含條目的 en/jp，代表舊譯不一致；
   - **他義**：不含，代表範圍太寬。
   - 只有可比對的 EN/JP 一致才判同義或他義；兩者不一致，或沒有對齊（含只剩標籤的對齊），判**未知**。

   報告與網站「詞彙範圍」分頁顯示這兩個數字。
2. **處置原則**：
   - 某組 ≥5 單位且 ≥80% 為他義 → 縮小範圍（`not_files: family:/group:`）；若他義的譯法集中於一種 → 加 `also` 或另立條目。
   - 同義缺漏 → 不改範圍，列入 D 的複查候選。
   - 其他 → 留為提案。
3. **這次的處置**：處理前 20 條，占缺漏的 71%。明確的直接改在分支上，邊界的留提案，全部列給使用者在合併前審閱。

## D. 舊譯複查與基準樣本

**基準樣本**

- `lct gold sample` 依固定種子，從每個族群抽 20 個非 copy 單位，共約 320 個，寫入 `rules/gold.yaml`（key、族群、來源、空白判定）。
- 網站新頁 `#/gold` 列出樣本的 KR/JP/EN/TW。每個單位可選「正確／有誤／不確定」並附說明，選完後複製判定行貼到對話；skill 用 `lct gold set` 記錄。
- `lct gold report` 依族群與來源算正確率，網站也顯示。
- 之後每次大改規則或重翻，就對同一份樣本重新判定比較。

**複查候選**

- `lct audit` 依訊號把舊譯排序。訊號包括：
  - 不一致群組成員；
  - C 判為同義的缺漏；
  - 格式警告；
  - 長度比異常。
- 依族群優先序分波輸出，每波上限可設，並估算費用（依 batch log 的每單位平均花費）。
- `--to-file` 會把一波依訊號組合各寫一份 `rules/requeue/<date>-audit-<topic>-<訊號>.yaml`（先檢查全部目標檔都不存在才寫，否則一份都不寫）；每份的繁體中文提示只描述該組合的訊號，並說明要保留原措辭、只修正問題。
- 這次只產生第一波的候選報告，不提交重翻申請。

## 非目標

- 不讓模型自動判定譯文正確與否來取代人工基準。
- 不使用 namu.wiki、wikiwiki.jp，它們被網站擋。
- 這次不重翻任何舊譯，不花翻譯費用。
- 不改送出檢查的嚴格度（詞彙仍只警告）。

## 驗收

- **A**：
  - 預覽頁比較同一單位改前後的指引組合；
  - 每批指引總量 ≤ 34 KB；
  - `rules lint` 無錯。
- **B**：
  - 報告列出補了幾條、各來源占比；
  - 抽 20 條人工可核對的出處。
- **C**：前 20 條的處置清單與應用率變化（改範圍後重算）。
- **D**：
  - 樣本頁在 400px 不橫向捲動；
  - `gold report` 在空判定時輸出 0 筆；
  - `audit` 第一波候選數與估計費用。
- **全部**：`go vet ./... && go test ./...`、site 的 test、typecheck、build；最終整支審查後才請使用者同意合併。
