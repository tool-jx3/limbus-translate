# 翻譯預覽：單位送翻時拿到什麼、送出時會怎樣

日期：2026-11-06。狀態：草稿（已併入實作者角度檢查的回答），待使用者核可。

## 目的

使用者想實際看到一個單位送去翻譯時，譯者拿到哪些文字：
- 哪些檔案：指引、提示詞；
- 哪些詞彙；
- 最後送出時會是什麼狀態。

用途是檢查規則：
- 分群與路由是否把對的指引、詞彙組進批次；
- 詞彙的 `units` 範圍是否合理；
- 現有譯文在現行規則下會被收下、警告還是退回。

現在要知道這些，只能讀程式或等批次真的發出去。批次檔（`work/batches/<id>.json`）只在 CI 裡暫存，不保存。

使用者選定：
- 位置：網站檔案頁加上 `lct` 指令（兩者都要）；
- 時間點：用現行規則模擬。也就是「現在把這個單位送翻會得到什麼」，以及「它現有的譯文用現在的送出規則檢查的結果」。不保存歷史批次。

## 目標

1. `lct batch preview <key> [--json]` 印出這個單位單獨送翻時的批次，加上送出檢查的結果。批次與 `lct batch next` 產生的格式相同（`schemas/batch.schema.json`）。
2. `lct site` 為每個 KR 檔案輸出預覽資料。網站上每個單位都有「翻譯預覽」，顯示兩個分頁：
   - 組合：結構化列出指引、詞彙、keywords、上下文、必須保留的內容、原文與輔助語言、待譯原因與舊譯，以及紀錄與送出檢查；
   - 全文：譯者實際讀到的文字，依序是 `prompts/translate.md`、批次 `guides` 列出的每份指引，最後是批次 JSON。可以一鍵複製。
3. 預覽與實際批次走同一份程式：
   - 組批次直接用 `assemble`；
   - 送出判定從 `(*submission).unit` 抽出成純函式，`Submit` 與預覽共用。
   - 這樣以後改規則或改程式，預覽不會跟實際行為分岔。

## 非目標

- 不模擬 `batch next` 的切批（同檔其他待譯單位會不會併進同一批、併進哪幾個檔案）。預覽固定是「只有這個單位的批次」。
- 不保存或回放歷史批次。紀錄上的 `batch`、`model`、`rules`（規則 commit）、`since` 照實顯示，但不重建當時的批次內容。
- 不呼叫模型，不產生譯文。
- 審核頁、搜尋頁的入口這次不做，只做檔案頁。

## 反目標（做到了也算失敗）

- 預覽寫入任何狀態：租約、嘗試次數、暫定詞、紀錄。預覽必須是唯讀的。
- 預覽與實際批次用兩套邏輯，久了不一致。網站上看到的與 `batch next` 給的不同，比沒有預覽更糟。
- 網站資料或 `lct site` 時間大幅膨脹，拖慢 pages 部署。

## 做法（已選）

考慮過三種：

| 做法 | 內容 | 取捨 |
|---|---|---|
| A. 每檔一份精簡預覽資料（選用） | `lct site` 用 Go 的預覽函式為每個檔案算出每個單位的「組成」：指引編號、詞彙條目編號、keywords、上下文單位編號、keep、待譯項目、紀錄、檢查結果。共用的部分寫一次：指引全文、提示詞全文、每檔的詞彙條目表。瀏覽器點開預覽時才載入該檔，再組回批次 JSON。 | 資料量小。只有 Go 一套規則邏輯。瀏覽器只做「查表組回」，用跨語言契約測試保證組回的 JSON 與 Go 產生的一字不差。 |
| B. 每單位存完整批次 JSON | 272,875 個單位 × 約 2 KB | 約 500 MB 以上，不可行 |
| C. 瀏覽器端重算 | 把路由、詞彙比對、指引選擇移植到 TypeScript | 兩套邏輯，正是反目標 |

## 已決定的細節

### 「單獨送翻」的批次怎麼來

- 單位在待譯清單中：用它的待譯項目，包括 reason、prev_kr、prev_zh、draft、hint 與 refs。
- 單位不在待譯清單、但有非 copy 的紀錄：用 `lct requeue` 會加的項目，也就是 reason `requeue`、prev_zh 是紀錄的譯文、沒有 hint。要共用 requeue 建項目的程式，不要另寫。
- 沒有紀錄也不在待譯清單：reason `new`。
- 紀錄是 copy 的單位不會送翻（requeue 也略過它們）：
  - CLI 回使用者錯誤（exit 1），說明它是 copy；
  - 網站不顯示預覽按鈕，改顯示「copy：識別碼或各語言相同，不送翻」。
- 不會送翻的情況與 `lct requeue` 一致：copy 之外，凍結檔案（`lct.yaml` 的 `frozen`，目前是空的）的單位也標示「不送翻：凍結檔案」，批次照樣組出來供參考。human、fallback 的紀錄 requeue 預設會送，預覽照常。
- 批次帶的是真實的待譯項目（reason、prev_kr、prev_zh、draft、hint、refs）。attempts、last_error 與租約不屬於批次內容，只在「狀態」一欄顯示。
- 批次 id 固定為 `preview`。上下文的範圍依 `contextReach(1)`，也就是實際只送這一個單位時的範圍（前後各 1 個元素）。
- 預覽要另外標示目前的狀態：
  - 單位有 `needs_review` 旗標時，標示「等人處理，現在不會發出」；
  - 單位已被租給某批次時，標示「已租給批次 X」。
  - 兩種情況批次內容照樣組出來。

### 送出檢查

- 檢查的是紀錄現在的譯文（`zh`），套用的就是 `Submit` 判定新譯文的那一段：
  - 正規化（`validate.Normalize`、`NormalizeKeywordSpace`）；
  - `CheckNewTerms`；
  - term-missing 依 `check: hard`、族群 `glossary: warn` 與 note 是否寫出原詞來升級；
  - 收下時另外檢查 `foreignNameIssues`。
- note 用這個 key、`kr_sha` 與現在 KR 相同的譯者說明，依 store 中的順序以換行合併（與網站 `nt` 欄位相同），再交給判定函式，就像 `Submit` 收到的一個 `note`。
- 每個非 copy 的紀錄都檢查，並標示來源：fallback 標「替代文字（EN 或 KR），不是譯文：結果僅供參考」，human 標「人工譯文」。
- 結果有三種：退回（有 hard）、收下但有警告、收下。每個問題列出 code、severity、class 與 message。
- 沒有紀錄時寫「沒有譯文可檢查」。
- 紀錄的 `kr_sha` 與現在 KR 不同時照樣檢查，但標示「這是舊 KR 的譯文」。
- 協定層的錯誤是送出當下才有的，預覽不模擬。這類錯誤包括 lease-lost 與 not-in-batch。

### 紀錄的狀態

- 顯示 origin、model、batch、since、rules（規則 commit），以及這個 commit 是否就是現行規則。
- 也顯示 flags；在待譯清單中時再顯示 attempts 與 last_error。

### CLI

- 指令是 `lct batch preview <key> [--json]`。
- CLI 與 `lct site` 用同一個「預覽輸入」載入函式取得 tw store、raw 三語、規則、foreign names、keyword names、生效中的暫定詞。兩者讀的本來就是同一個 tw worktree 的 store（`openStore` 與 `openTWStore` 指向同一處），共用載入函式是為了保證 `Env` 一致。注意 `openBatchEnv` 現在不填 `KeywordNames`，預覽要填，否則正規化與 `Submit` 不同。
- `--json` 輸出 `{batch, check, record, pending, notes, state}`，其中 `batch` 就是批次 JSON。
- 文字模式列出摘要：族群、指引清單、詞彙條目（kr → zh、check）、keywords、上下文行數、檢查結果與問題、紀錄狀態。
- exit code：成功 0；key 不存在、單位是 copy 等使用者錯誤 1；系統錯誤 2。
- 測試要確認：執行前後 store 的檔案一字不變。

### 網站

- 路由用新的頁面：`#/pv/<file>?ptr=<pointer>`。
  - 檔案頁表格與劇本兩種檢視的每一列都有「預覽」連結。
  - 預覽頁有回到檔案該單位的連結。
- 預覽頁頂端寫「依規則 `<rules commit 前 7 碼>` 模擬」，用的是 meta 的 rules_commit。
- 資料：
  - 共用檔一份：提示詞全文、指引全文（約 120 KB）；
  - 每個 KR 檔一份預覽檔，點開時才載入。
- 一個單位的預覽只需要三樣資料：該檔的檔案資料（`data/files/…`，檔案頁已載入）、該檔的預覽檔、共用檔。不跨檔載入。`storyContext` 本來就只看同一個檔案；keywords 的名稱在預覽檔裡存成每檔一張表（id → 名稱）。上下文的 `zh` 是 `lct site` 執行當時紀錄的譯文；它與檔案資料的 `zh` 不同時，預覽檔要自己帶。
- 「全文」分頁的批次 JSON 必須與 `batch next` 寫出的檔案逐字相同：`writeJSONFile` 的格式是兩格縮排、不跳脫 `<` `>` `&`、結尾換行，鍵的順序依 Go 結構。
- 契約測試：Go 測試用固定資料產生某幾個單位的預覽檔，以及 `writeJSONFile` 格式的完整批次 JSON，放進 `site/fixtures/`。TS 測試用預覽檔組回批次 JSON 文字，必須與 Go 的檔案逐字相等。這比照現有 fixture index 測試的做法。fixture 要涵蓋這些單位：劇情單位（有上下文、有 speaker 指引）、非劇情單位、含 `[ID]` 的單位（有 keywords）、有 `<` 標籤的單位、待譯單位（有 draft 或 hint）。

### 預算

這是要回報的數字，不是建置的關卡。合併本來就要使用者同意，數字在那時一併報告。驗收時用真實資料量測：
- 預覽資料總大小，以及 `lct site` 多花的時間。
- 預估資料增加在 60 MB 以內、時間增加在 50% 以內。超過時先回報使用者，再決定要精簡什麼（例如上下文改由瀏覽器從檔案資料取文字、只存編號）。

## 留給實作者決定

- 預覽檔的欄位名稱與壓縮方式（短鍵、編號表），以及共用檔的切法。
- 抽出的送出判定函式的名稱與簽名，以及 `assemble` 為單一單位要怎麼呼叫：自己組 `part`，或抽一個小包裝。
- 預覽頁的版面細節：分頁、摺疊、複製按鈕的位置。要沿用現有樣式變數，400px 寬時不得橫向捲動整頁。
- 文字模式的確切排版。
