# 依遊戲行為的譯文檢查 — 設計

> 狀態：待使用者確認。已請一位沒參與討論的實作者讀過（2026-11-15）：`qmark-count` 的範圍依他的問題改成只看罪孽型敵人（我的決定，依據報告 `04-other.md` §4），試算數字依他重算的結果更正。使用者已決定（2026-11-15）：新檢查在目前階段**全部只當警告**，不擋新翻譯。
> 依據：研究報告 `docs/research/2026-11-15-game-text-logic/`（以下稱「報告」）、審核頁 spec `docs/superpowers/specs/2026-11-03-review-page-design.md`（以下稱「審核頁 spec」）。

## 1. 目的

報告從遊戲程式讀出了「譯文怎麼寫會顯示錯」的規則。使用者要把這些規則做成檢查，讓不符合的現行譯文出現在網站審核頁的「檢查警告」分頁，像其他警告一樣可以複製 ID、在對話中決定要改還是確認沒問題。

## 2. 目標、非目標、反目標

**目標**

- 新增 13 個檢查代碼（§5），不符合的單位出現在審核頁的檢查警告分頁與建置報告的警告統計
- 每個新代碼在審核頁有中文名稱與一句說明；警告卡上看得到這個單位具體哪裡不符（檢查的訊息）
- 新警告與既有警告用同一套 ID、同一個確認清單（`rules/accepted.yaml`、`lct accept`）

**非目標**

- 不擋新翻譯：所有新代碼都是警告。之後要把哪些升級成「新翻譯直接退回」，另外決定
- 不修正現行譯文。檢查上線後出現的項目，照既有流程在對話中處理
- 不檢查「KR 有關鍵字連結、譯文沒有」（報告推算 429 處，多半不是錯）
- 不處理 `excludeAutoLink`：譯文目前無法自行增加這個旗標（語言包的非文字欄位照抄 KR），要支援得另外設計
- 不改 `guides/`：把這些規則寫進翻譯指引是另一件事
- 不檢查報告中已由建置保證的結構（檔名、欄位集合、陣列長度、非字串值、劇情列數）與既有檢查已涵蓋的項目（`[ID]`、佔位符、標籤、`<noparse>` 內容）

**反目標**（技術上可行但算失敗）

- 網頁與建置報告對同一批單位算出不同的警告數（審核頁 spec 的反目標）
- 為了網頁另寫一份 TypeScript 的檢查邏輯
- 新檢查讓既有警告的 ID 改變，使 `rules/accepted.yaml` 裡已確認的項目重新冒出來
- 把本專案指引刻意要求的寫法（狀態名稱後加半形空格）報成誤連結

## 3. 限制

- 沿用審核頁 spec §3 的全部限制
- 檢查的依據是 2026-11-12 版遊戲的靜態分析，沒有在遊戲中逐項確認；訊息與說明不可以寫成「遊戲一定會如何」，要寫「依遊戲程式推算」
- 檢查只用 `raw`（KR）與翻譯紀錄算得出來的資料，不讀遊戲檔案
- `go vet ./... && go test ./...`、`cd site && npm ci && npm test && npm run build` 要通過

## 4. 做法

- **A（採用）：加進 Go 的 `validate.Check`，需要整包資料的檢查由呼叫者提供一份預先算好的「遊戲文字資訊」。** 審核頁的警告本來就來自 `validate.Check`，建置報告也是；新檢查加在同一處，網頁、建置報告、`lct accept` 自動一致。需要其他單位資料的檢查（關鍵字名稱表、上一個同步等級的文字、`SkillTag` 的名稱）由建置與網站匯出各自在開始時從 KR 檔與翻譯紀錄建好一份資訊，放進 `validate.Context`；沒有提供時這些檢查略過。
- **B：另做一個「整包檢查」步驟，產生新的審核項目種類。** 可以自由設計項目的形狀，但要新增 ID 種類、確認清單、網頁分頁與 `lct accept` 的分支，而每一項其實都能歸到單一單位上，換不到東西。
- **C（不考慮）：在瀏覽器裡跑檢查。** 違反審核頁 spec 的反目標。

使用者交由我決定做法，採 A。

## 5. 新檢查

全部是警告（`validate.ClassStyle`）。「範圍」以語言包檔名（不含資料夾時指根目錄的檔）與欄位表示；檔名以「去掉 `.json` 後，到第一個 `-` 或 `_` 之前的部分」判斷族群（`Skills_personality-01.json` 是 `Skills`，`AbEventsResultLog.json` 不是 `AbEvents`）。「現況」是以 `raw-20261112` 與 `tw` 7fccf1d 試算的單位數，供實作後核對數量級，不是測試的固定值；數字與規則不一致時以規則為準。

### 5.1 `keyword-link`

**範圍與處理方式**（報告 `03-keywords.md` 的表）：

| 族群 | 欄位 | 先做標籤處理 |
|---|---|:-:|
| `Skills` | `levelList[].desc`、`levelList[].coinlist[].coindescs[].desc`、`…coindescs[].summary` | ✔ |
| `Passive`、`Passives` | `desc`、`summary` | ✔ |
| `EGOgift` | `desc`、`simpleDesc[].simpleDesc` | ✘ |
| `PanicInfo` | `lowMoraleDescription`、`panicDescription` | ✘ |

**算出譯文裡會被連結的名稱**，依遊戲的做法（`docs/research/2026-11-15-game-text-logic/method/kwsim.py` 是可對照的重現腳本）：

1. 名稱表：`Bufs*.json` 每一筆的 id、譯文的 `name`、KR 檔上的 `excludeAutoLink`。名稱是空的或不分大小寫等於 `Unknown` 的不收；有 `excludeAutoLink` 的不參加比對。譯文的 `name` 取「這個單位實際會用的翻譯紀錄」（與警告挑單位的條件相同）；沒有可用紀錄或紀錄是照抄（copy）的，取 KR 的名稱。
2. 標籤處理（只有打 ✔ 的欄位）：文字裡每個 `\[.*?\]`，括號內不是 `Bufs*.json` 的 id 的，換成一個不可能是名稱一部分、也不在允許清單裡的字元（例如 `<`）。這一步讓 `名稱[TabExplain]` 後面變成不觸發的字元。
3. 找出所有名稱的所有出現位置；依名稱長度由長到短逐一採用，與已採用範圍重疊的丟掉；前一個或後一個字元是 U+200B 的丟掉。
4. 留下的每個名稱看後面的字：
   - 後面（至多隔 1 個字元）是譯文 `BattleUIText.json` 的 `resonance` 文字，或去掉空格後是 `perfect_resonance` 文字 → 不連結。兩個字串同樣取自翻譯紀錄，沒有時取 KR 的。
   - 名稱在文字結尾，或下一個字元是空白（Unicode 的空白，含全形空格、換行、U+00A0）、數字（Unicode 的十進位數字，含全形）、或 `・「」『』.,/&;` 其中之一 → 連結。
   - 其他 → 不連結。

**判斷是不是誤連結**：對每個會連結的名稱，取「譯名等於這個名稱的全部 id」。只要 KR 文字含有其中任何一個 id 的 `[id]`，或含有其中任何一個 id 的 KR 名稱（非空），這個連結就算 KR 有提到，不報。全部都沒有才報。

這個定義刻意不比較「KR 會不會連結」：本專案的指引要求 KR 寫韓文狀態名的地方，譯文寫官方中文名並加半形空格，所以譯文有連結而 KR 沒有（KR 後面接助詞）是正常的。要抓的是 KR 根本沒提到那個狀態的情形，例如把狀態 `ConfessionThirdPhase` 譯成「～」之後，「1～2層」被連到它。

訊息列出每個誤連結的名稱與它的 id，例如：`「～」會被遊戲連到狀態 ConfessionThirdPhase，但 KR 沒有提到它（依遊戲程式推算）`。

已知的近似：遊戲只對 enum `BUFF_UNIQUE_KEYWORD` 的成員做自動連結，`Bufs*.json` 有 54 個 id 不是成員；這裡把全部 id 都當成會連結。會多報的情形是「這 54 個 id 的譯名剛好出現在文字裡、後面是觸發字元、而 KR 沒提到」，預期極少，出現時確認即可。

### 5.2 `level-diff`

同步等級比較畫面把新舊兩級的文字逐行比較，整行相同的不標示。KR 兩級相同、譯文卻不同的行會被誤標。

- 「上一級」：同一個技能的 `levelList` 裡，`level` 比這一筆小的當中最大的那一筆（`level` 不一定連續，例如 1、3、4）。沒有更小的就沒有上一級，不檢查。
- 技能說明：這一級與上一級的 `desc` 各以 `\n` 切成行。對每個行號 i，KR 兩級都有第 i 行且完全相同，而譯文兩級的第 i 行不同（其中一級沒有第 i 行也算不同）→ 報。
- 硬幣說明：`coinlist[c].coindescs[d].desc` 與上一級同樣 `c`、`d` 位置的 `desc` 比較，規則同上；上一級沒有這個位置就不檢查。
- 警告掛在**較高那一級**的單位上。兩級的譯文都取實際會用的翻譯紀錄；任何一級沒有可用紀錄就不檢查。
- 訊息指出第幾行、與哪一級不同，例如：`第 2 行在 KR 與等級 1 相同，譯文不同：「…施加3層麻痺 」／「…施加3層 麻痺」`（各截到 40 字）。一個單位只報一次，訊息列出第一個不同的行與總行數。

## 6. 需要整包資料的檢查怎麼接

- `validate.Context` 增加兩樣：單位的指標（`Pointer`，用來判斷欄位；空的時候，所有要看欄位的新檢查都略過），以及一份「遊戲文字資訊」（指標，nil 時 `keyword-link` 與 `level-diff` 略過）。
- 「遊戲文字資訊」由一個函式從兩樣東西建出來：KR 的檔案內容（`Bufs*`、`BattleUIText`、`Skills*`），以及「給單位 key，回傳它實際會用的譯文」的查詢函式。建置與網站匯出都呼叫這同一個函式，並傳入各自既有的「這個單位用不用得上紀錄」的判斷，確保兩邊結果相同。
- 建置（`internal/build`）與網站匯出（`internal/site`）的 `validate.Check` 呼叫處帶上 `Pointer` 與這份資訊。`lct accept` 用的是網站匯出的同一套計算，自動跟上。
- 其他呼叫處（`lct batch submit`、`lct adjust add`、`lct validate`、bootstrap）：知道指標的就帶上 `Pointer`，讓只看單一單位的新檢查也在那裡以警告出現；不提供「遊戲文字資訊」。這些地方原本怎麼呈現警告就怎麼呈現，不改行為。
- 既有檢查的代碼、訊息、順序都不變；新檢查的問題接在既有的後面。既有警告的 ID 不變。

## 7. 審核頁

- `site/src/review/names.ts` 為 13 個新代碼各加名稱與一句說明（§5 表的「名稱」欄；說明用一句話講後果，例如 `keyword-link`：「依遊戲程式推算，TW 的這些字會被連成 KR 沒提到的狀態」）。
- 警告卡沿用既有樣式；新代碼不需要在 TW 文字上畫記號（`marks.ts` 不加），具體位置由檢查的訊息說明。`marks.test.ts` 裡列舉有記號代碼的測試不必改。
- ID、分組（代碼＋KR＋TW）、確認流程都不變。`level-diff` 的同一組 KR／TW 在不同技能可能一個報、一個不報：項目只列出有問題的單位，確認之後同樣文字的單位都算確認，可以接受。

## 8. 測試

- `internal/validate`：每個新代碼至少一個會報、一個不報的案例；`keyword-link` 另外涵蓋——名稱後接空格、數字、`」`、句尾會連結；後接「，」「。」中文字、`<`、`[TabExplain]`（有標籤處理的欄位）不連結；沒有標籤處理的欄位（`EGOgift` 的 `desc`）裡 `名稱[TabExplain]` 同樣不連結（名稱後面是 `[`）；長名稱優先；`excludeAutoLink`；U+200B；共鳴例外；KR 以 `[id]` 或 KR 名稱提到時不報；同名多個 id 任一被提到就不報；專案裡兩個在遊戲中確認過的句子（「攻擊等級+1」、「加斥我援」）會被算成連結。
- `level-diff`：`level` 不連續、上一級少一行、硬幣位置在上一級不存在。
- 沒有 `Pointer` 或沒有遊戲文字資訊時，對應的檢查不報、也不出錯。
- 建置與網站匯出對同一份 fixture 算出相同的新警告（沿用審核頁 spec §10 釘住兩邊一致的測試，fixture 加上能觸發 `keyword-link` 與 `level-diff` 的資料）。
- 既有測試全部維持通過；`rules/accepted.yaml` 現有的 ID 仍然對得上目前的警告（實作後以真實資料跑一次 `lct accept --tidy --dry-run` 之類的方式確認沒有因為這次改動而失效的條目）。
- 網站：`names.ts` 的新代碼有名稱；既有測試通過。

## 9. 交給實作者決定

- 「遊戲文字資訊」放在哪個套件、型別與函式的名稱、內部用什麼資料結構比對名稱（名稱約 1,500 個、要檢查的欄位約 29,000 個，直接比對或建 Trie 都可以，只要建置時間沒有明顯變長）。
- 訊息的確切用字（須符合 §3：不可以寫成確定的事實）。訊息用英文還是中文照既有檢查的慣例。
- 檔名族群與欄位的判斷寫成什麼樣的表。
- 測試 fixture 的形狀。

## 10. 上線後預期看到的東西

以目前的資料，審核頁的檢查警告分頁會多出大約 210 個單位（`keyword-link` 130、`level-diff` 61、`newline-space` 9、`page-count` 5、`bracket-text` 4、`bullet-count` 2），依「代碼＋KR＋TW」分組後項目數會少一些。建置報告的警告統計同步增加。這些項目照既有流程處理：要改的寫成人工調整，沒問題的用 `lct accept` 確認。
