# 專有詞彙一致：詞彙表檢查、暫定詞、合批與發放順序

## 目的

讓新翻譯的檔案統一專有詞彙：詞彙表有的詞一定照用（例外要說明），同一次更新裡第一次出現的新名詞，後面的批次跟著用；舊譯文與詞彙表不合的地方列在網頁上，由使用者逐詞決定怎麼處理。同時減少每批的固定開銷。

## 現況（2026-11-05 的檢查）

- 驗證器只擋 `forbidden`（禁用譯法），不檢查有沒有用指定譯法；`glossary/terms.yaml` 595 條中只有 72 條有禁用譯法。建置與審核頁的檢查也沒有帶詞彙表（`validate.Context` 沒有 `Terms`）。
- 原文含詞彙表的詞、譯文沒用指定譯法的比例：這次更新 Claude 新翻 2/173（兩處都是合理例外：「시즌」在台詞裡是季節、「탐식의 재림」是既有卡包名）；先前的 Claude 譯文 348/8292；Paratranz 2740/73665。先前的偏高，主要因為 455 條詞是事後加的。
- 一批只放一個檔案：這次 71 句分成 15 批，9 批只有 1～2 句；每批都重讀提示詞與指引。
- 同一次更新的新名詞，各批不共享：譯者的 note 已指出「우레 → 雷鳴，Bufs_Mirror8 有同名效果，應統一」「『狂獵希斯克利夫』與『狂獵 希斯克利夫』宜統一」。
- 定義關鍵字與效果名稱的檔案（`BattleKeywords*`、`Bufs*`）大多屬 `other` 族群，最後才發放；用到這些名稱的說明文字先翻，批次的 `keywords` 拿不到名稱。

## 目標

1. **詞彙表譯法檢查**：原文含詞彙表的詞（依現行的命中規則：`files`、`match: word` 等）而譯文沒有指定譯法時，送出時退回；該單位的 `note` 寫出這個詞的韓文原詞時，視為譯者說明過的例外，收下並記成警告，出現在審核頁。建置與審核頁對既有譯文同樣檢查，記成警告（不退回、不影響建置）。
2. **暫定詞**：譯者在輸出裡登記新詞（韓文 → 譯法）；送出時記下；之後發放的批次，句子含同一個韓文詞就帶上它，並和詞彙表一樣檢查（例外要寫 note）；審核頁列出所有暫定詞，使用者確認的加入 `glossary/terms.yaml`，否決的不再使用。
3. **小檔案合批**：劇情以外的族群，一批可以裝同族群的多個檔案，直到單位數上限；劇情批次維持一個檔案（要前後文）。
4. **先發放定義名稱的檔案**：`BattleKeywords*`、`Bufs*`（`batch.KeywordNames` 讀的那些檔）的待譯單位，比其他所有族群先發放。
5. **舊譯文不合詞彙表**：審核頁依詞分組列出既有譯文中沒用指定譯法的地方，使用者看過後逐詞決定（沿用審核頁的複製 ID → `/review-page` 流程）。

## 非目標

- 自動改寫或重翻舊譯文：第 5 項只列出，由使用者決定。
- 自動翻譯記憶（從既有譯文找相似句）：之後可另做。
- 從譯者 note 的自由文字解析新詞：新詞只從輸出的 `terms` 欄位來。
- 改變劇情批次的切法。

## 反目標

- 合理的例外被反覆退回、耗盡嘗試次數而變成 needs_review（例外必須能用 note 通過）。
- 暫定詞未經使用者確認就寫進 `glossary/terms.yaml`（規則只在 `glossary/` 等，由人或 skill 經使用者決定後改）。
- 審核頁被數千筆逐句的警告淹沒：既有譯文的詞彙表警告要依詞分組。
- 合批後劇情批次失去前後文。

## 做法比較（第 2 項）

| 做法 | 取捨 |
|---|---|
| **A. 譯者在輸出裡明確登記新詞（採用）** | 精準、可控，只共享譯者判斷為新詞的；要靠譯者記得登記（提示詞明確要求） |
| B. 自動翻譯記憶 | 不用譯者做事，也涵蓋舊詞；韓文沒有分詞，「少見詞」難判斷，批次變大變雜，只是參考不是約定 |
| C. 只靠合批與發放順序 | 不多做機制；跨族群、跨批次的仍顧不到 |

使用者選 A。第 1、3、4、5 項各只有一種合理做法。第 1 項「退回，note 寫明原詞才收下並列入審核」由使用者確認。

## 決定的部分

### 1. 詞彙表譯法檢查

- 新的檢查碼 `term-missing`（`ClassContent`）：對每個命中的詞彙表條目（`rules.GlossaryHits`），譯文不含條目的 `zh` 時記一則。訊息寫出韓文原詞、指定譯法，以及「若是合理例外，在 note 寫出原詞與理由」。
- 嚴重度：
  - `batch submit`：預設 `hard`（退回、計嘗試次數）；該單位輸出的 `note` 含有條目的 `kr` 時改為 `warn`（收下，記入 warnings）。
  - 建置與審核頁（`Existing: true`）：一律 `warn`。
- 不檢查：欄位規則判定不翻譯的單位（`copy`）；條目的 `zh` 與 `kr` 相同的條目。
- 建置報告的 `warnings` 計數會多出 `term-missing`；審核 Issue 不收警告，不受影響。

### 2. 暫定詞

- 輸出格式：每個單位可有 `terms`，陣列，每項 `{"kr": "<韓文詞>", "zh": "<譯法>"}`；`schemas/batch-out.schema.json` 增加此欄位。`kr` 必須出現在該單位的 KR 原文中，`zh` 必須出現在該單位的譯文中，否則該項不記（送出結果列出被略過的項與原因，不退回整句）。
- 儲存：`batch submit` 把收下的單位登記的詞寫進 `tw` 的 `.meta/terms.jsonl`（狀態，只經由 `lct` 寫），每行記 `kr`、`zh`、`key`、`batch`、`raw_tag`、`time`。同一個 `kr` 已有暫定詞時不覆蓋；譯法不同的另記為衝突，留給審核頁顯示。
- 生效：之後發放的批次，單位的 KR 含某個暫定詞的 `kr`、而 `glossary/terms.yaml` 沒有同樣 `kr` 的條目、`rules/declined.yaml` 也沒有否決它時，把它放進批次的 `glossary`，標 `provisional: true`。驗證時和詞彙表條目一樣做 `term-missing` 檢查。
- 審核：`lct suggest`（審核頁「規則建議」分頁）把每個暫定詞列成一個項目（新的種類，例如 `term/new/…`），附登記它的句子與用到它的句子、衝突的譯法。使用者經 `/review-page` 或 `term-decision` 決定：確認 → 寫入 `glossary/terms.yaml`（`status: approved`，附 `evidence`）；否決 → `rules/declined.yaml`，之後不再放進批次。確認後的條目由詞彙表接手，暫定詞紀錄保留但不再生效。
- 暫定詞跨次更新持續生效，直到被確認或否決。

### 3. 小檔案合批

- 劇情以外的批次：依發放順序取第一個有可發放單位的檔案，之後可接同族群、其他檔案的單位，直到 `batch.max_units`（現行 40）；劇情批次（`batch.IsStory`）維持單一檔案與 `context`。
- 批次格式：每個單位加 `file`；批次頂層的 `file` 改為該批第一個檔案並另有 `files`（全部檔案，依發放順序）。`schemas/batch.schema.json` 跟著改。`guides` 是同族群共用的指引加上各單位說話者的角色指引。
- 提示詞與 skill：說明單位的 `file`；依檔名區分語氣時以單位的 `file` 判斷。

### 4. 發放順序

- 待譯單位的發放，先發 `BattleKeywords*` 與 `Bufs*`（與 `batch.KeywordNames` 讀的檔相同的判定）的單位，再依 `guides/routing.yaml` 的族群優先順序。這些檔案的批次也可依第 3 項合批（同族群內）。

### 5. 舊譯文不合詞彙表：審核頁

- 審核頁「檢查警告」分頁，`term-missing` 依詞彙表條目分組：每個條目一個項目，顯示韓文原詞 → 指定譯法、不合的單位數、每個單位的原文與譯文（指定譯法該出現處標示）、譯者 note（例外說明）。項目 ID 以條目為單位；也可只複製其中幾個單位。
- 使用者看過後，在 Claude Code 用 `/review-page` 貼上 ID 並說明決定。這個 skill 依決定執行（既有能力）：
  - 保留這些譯法 → `bin/lct accept`（記入 `rules/accepted.yaml`，之後不再列出）；
  - 改用指定譯法 → `bin/lct requeue --to-file`（重翻要求檔，附提示「依詞彙表把 X 譯為 Y」），下次建置時重翻；
  - 詞彙表本身太寬（例如「날개 → 翼」不適用身體部位的翅膀）→ 修改 `glossary/terms.yaml`（`files`、`match`、`notes`），重建後不再列出。
- 不自動改寫：要用機械替換時，由 skill 在使用者同意後寫改寫規則（`rules/rewrite/`，既有機制）。

## 限制

- 遵守 `CLAUDE.md`：規則只在 `guides/`、`glossary/`、`rules/`；狀態只經由 `lct`；`raw`、`tw`、Release 只由 CI 寫入；所有 `lct` 指令支援 `--json`；skill 與 `prompts/` 不寫模型名稱。
- 提交前 `go vet ./... && go test ./...`；動到 `site/` 另跑 `npm test`、`npm run typecheck`、`npm run build`。
- skill 的 `allowed-tools` 與契約測試（`cmd/lct/contract_test.go`）一起更新。
- README 說明新的檢查、暫定詞、合批與發放順序。

## 留給實作者

- `term-missing` 訊息的確切文字、警告項目 ID 的格式（沿用現有 `warning/<code>/…` 的雜湊方式）。
- `.meta/terms.jsonl` 的欄位名稱與衝突的記法。
- 暫定詞在「規則建議」的種類名稱與顯示樣式。
- 合批時族群判定與單位排序的細節（沿用現行 `batch.Next` 的檔案順序）。

## 驗收

- 送出時：缺指定譯法且 note 沒有原詞的單位被退回；note 寫了原詞的收下並有 `term-missing` 警告。以這次的兩個例子（「시즌」「탐식의 재림」）各做一個測試。
- 暫定詞：A 批登記「우레 → 雷鳴」後，含「우레」的 B 批 `glossary` 帶有它（`provisional: true`）；B 批沒用且沒寫 note 時退回；否決後不再出現。
- 合批：用這次更新的待譯清單重放，非劇情批次數明顯少於 15（同族群的小檔案合在一起），劇情批次不變。
- 發放順序：`BattleKeywords_Mirror8`、`Bufs_Mirror8` 的單位最先發放。
- 審核頁：真實資料上 `term-missing` 依詞分組，例如「자판기 → 自動販賣機」一組約 19 個單位；不會出現逐句數千筆的清單。
